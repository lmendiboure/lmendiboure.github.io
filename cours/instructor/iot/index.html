Teacher guide

Session 1
activity flow

For each block: what students do, what should be visible at the next STOP, and a few prompts worth using in the discussion.

01
Student activity until STOP 1

Map potential IoT systems to application domains

Students receive eight connected physical systems. For each one they choose a main application domain and, when useful, one secondary domain. They do not search for definitions or examples. Do not tell them in advance that the point is to demonstrate the breadth of IoT; let the overlaps and disagreements create that conclusion at STOP 1.

Expected before STOPEvery system has a main domain and several should also have a defensible secondary domain. The interesting output is disagreement between groups, not a perfect classification.
Useful for the discussion
  • Start from disagreements rather than correcting every card.
  • Useful ambiguous cases: vaccine shipment = Health / Logistics / Mobility; EV charging = Energy / Mobility / Smart city; school air quality = Environment / Health / Smart city.
  • Expert round: ask a fast group to defend one borderline case. “Connected”, “Internet-connected” and “interacts with the physical world” are not equivalent criteria.
  • The important observation is the breadth of physical environments, actors, infrastructure and constraints covered by IoT.
  • Close with: if these applications are so different, should they all use the same architecture and communication technology?

02
Student activity until STOP 2

Enter the campus mission and build architecture v1

The campus case is now presented as a full design brief: physical setting, 30 distributed measurement points, four signals, and two service outcomes. The visual shows only the physical environment — never a network solution. Students are positioned as the systems-design team, then invent their own components and information flows. Product and protocol names should not be used as architectural answers.

Expected before STOPA readable end-to-end architecture with several functional components and labelled information flows.
Useful for the discussion
  • Keep the mission brief visible when introducing the activity: students should know why they are drawing before deciding what to draw.
  • What did they treat as a component?
  • Separate function, physical component, technology and data flow.
  • One physical node can implement several functions.
  • Use contrasting student architectures rather than presenting a reference architecture immediately.
  • Expert round: after removing a component, students get one architectural move only. Ask what their chosen response fails to solve. This is a useful entry into redundancy, buffering, graceful degradation and alternate paths without teaching those as a catalogue.
03
Student activity until STOP 3

Reason about constraints in plain language, then name them

Students first work with questions such as “How far?”, “How much data?”, “How soon?” and “What can we rely on?”. They select the dimensions that matter and star three priorities. The formal vocabulary is intentionally revealed only during/after the STOP discussion.

Expected before STOPA defensible set of relevant constraints plus a clearly identified top three, expressed without requiring prior networking jargon.
Useful for the discussion
  • Use the groups’ plain-language answers first; only then attach the technical labels.
  • Map “How soon?” to latency, “How much data?” to data volume/throughput, “How far?” to range, and so on.
  • Different flows in the same architecture can legitimately have different priorities.
  • Reference vocabulary to reveal: range, data volume/throughput, latency, reliability, energy, scale, mobility, infrastructure, cost.
  • Expert round: compare one concrete arrow with the system-wide Top 3. If they differ, ask whether the global ranking is hiding an important flow.
04
Student activities 4–6 until STOP 4

Discover network shapes, attach technology names, then decide

This is the core scaffold of the session. The campus mission remains visible as a compact context strip. Activity 4 does not test prior knowledge: students start from four concrete questions (distance, data, energy, infrastructure), inspect five plain-language network shapes, and reveal the associated technology families. Activity 5 consolidates that map through the detective and a guided reference library. Activity 6 deliberately leaves campus for transfer cases, then returns to a campus checkpoint so students must state whether one family, a mixed design, or additional information is more defensible.

Expected before STOPStudents can explain the essential network shape behind Wi-Fi, Bluetooth LE, IEEE 802.15.4, LoRaWAN and cellular IoT, and can justify a deployment choice relative to explicit assumptions.
Useful for the discussion
  • No whole-class correction between Activities 4 and 5. The student page itself supplies the minimum information needed for the next phase, so teacher discussion does not spoil the detective.
  • Expert round in Activity 4: students must choose a network shape for new cases without naming a technology. This tests whether they can separate problem structure from product/standard recall.
  • Lead with plain concepts: nearby peer, local access point, low-power local building block, gateway-based wide area, operator-managed wide area. Attach jargon only after the shape is understood.
  • For IEEE 802.15.4, first say “basic local radio-transmission and channel-sharing rules”. Only then introduce PHY and MAC as the technical names for those responsibilities.
  • For cellular IoT, first use “base station + operator network”; RAN/core/licensed spectrum belong in the deeper layer, not the first explanation.
  • LoRaWAN and cellular IoT can both solve low-rate wide-area problems while implying very different infrastructure ownership.
  • Satellite/NTN is introduced as a path that may provide direct access or backhaul, not as a sixth interchangeable card.
  • Use the optional abstraction trap only after the guided discovery: LoRa ≠ LoRaWAN; IEEE 802.15.4 and LoRaWAN can be compared for a design decision without being the same abstraction level.
  • The side-by-side comparison and Claim Lab are for fast groups: Bluetooth LE radio-mode trade-offs, LoRaWAN classes/ADR, NB-IoT vs LTE-M, private vs operator infrastructure, NTN and spectrum-cost claims.
  • In deployment cases, the reference driver is a discussion anchor rather than a unique justification. Compare groups that chose the same technology for different reasons.
  • Campus checkpoint: do not force consensus on “one family” versus “mixed”. Ask instead which missing fact — power, coverage, traffic, latency or physical layout — could most change the answer. This is the transfer back from generic technology knowledge to the main case.
  • The “refuse to guess” challenge is important: missing requirements should block a premature technology choice.
05
Final student activity

Stress-test the original architecture

Students change one assumption, identify the requirement affected, and select a plausible architectural response. The free-text redesign note remains optional.

Expected at the endStudents can articulate: broken assumption → changed requirement → architectural response.
Useful closing point

An architecture is defensible only relative to assumptions and requirements. If groups tried the compound-failure challenge, they were allowed one architectural change for two failures. Use one answer to show why a response solving one failure may become insufficient when constraints combine. The final screen then asks four short retrieval questions before showing the session synthesis; let groups answer aloud before revealing. Converge on: Need → functions → architecture → flows → requirements → technology → challenge → revision.
