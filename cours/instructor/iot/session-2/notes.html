Instructor-facing facilitation notes · Session 2

Follow one message. Build the communication system.

Session 2 follows one concrete thread: a CO₂ sample from room B204 must reach the right service, be understood, and sometimes lead to a ventilation command whose real effect must be checked. The technical content remains dense, but the order is now deliberately problem-first.

Narrative rule: do not introduce a technical label as the starting point. First expose the engineering question in ordinary language, let students make one meaningful distinction, then give the formal term and finally attach technologies to the job they solve. Vocabulary is the name of an idea already encountered, not an entry ticket to the activity.

Four chapters structure the session: (1) who talks to whom, (2) which communication jobs are hidden in the path, (3) how applications exchange and preserve meaning, and (4) what the resulting system can actually guarantee. Keep referring back to the same B204 sample / ventilation command when a transition feels abstract.

Restitution contract: formalise after the student move. Activities 1, 2, 3, 6, 7, 8 and 9 use a STOP to name and stabilise the concept. Activities 4–5 are guided discovery: the problem solved by a technology is visible before its name is revealed. A wrong classification is discussion material, never a prerequisite for progress. Optional Challenge-me routes add depth without becoming part of the core path.

01
Activity 1 of 9

What kind of conversation is this?

Start from observable behaviour; name the interaction pattern afterwards.

5–6 min work · 5–6 min restitutionCore cap · 9 min
Operational trigger to stage

Use four concrete exchanges. For each one, ask only three plain questions first: who starts, who receives, and must the sender wait for anything before considering the exchange complete? Only after the choice should the labels one-way push, request–response, publish/subscribe and command–ACK be stabilised.

Watch for

Students should reason from waiting, receiver set and completion condition rather than from protocol familiarity.

Validate

The interaction pattern is a compact name for observable service behaviour.

Correct if needed

Do not start with “client/server”. It hides distinctions such as one sender to many subscribers or a command that needs an acknowledgement.

Landing point / transition

Land on: describe the conversation before choosing a protocol.

Reference plate / step further

Reference map: request/response · command/ack · publish/subscribe · observe/notify · event notification · streaming; one-to-one / one-to-many; direct vs broker-mediated.

02
Activity 2 of 9

Who speaks, and in what order?

Draw the sequence first; introduce “choreography” and “coupling” only after the dependency is visible.

7–8 min work · 5–6 min restitutionCore cap · 10 min
Operational trigger to stage

Reuse one exchange from Activity 1. Place the actors, then ask students to order the messages. Broker and Gateway are introduced only as possible roles when the scenario needs them. Once the sequence is visible, ask: if this actor disappears, who can no longer make progress?

Watch for

Whether students can explain the dependency in ordinary language before using the word coupling.

Validate

A static architecture shows possible paths; a message sequence shows what actually happens and who waits for whom.

Correct if needed

Broker is not a generic synonym for gateway. A broker is specifically an intermediary for publish/subscribe routing; a gateway may bridge, translate or proxy between environments.

Landing point / transition

Only now name the ordered interaction a choreography, and the visible dependency a form of coupling.

Reference plate / step further

Know actor/message roles: producer, consumer, gateway/proxy, broker; telemetry, query/response, command/ack, event/notification.

03
Activity 3 of 9

Five jobs hidden inside communication

Build a responsibility model from five engineering questions, not from protocol names.

6–7 min work · 5–6 min restitutionCore cap · 10 min
Operational trigger to stage

Present the supplier slide with MQTT, TCP, Thread and Wi‑Fi as if they were four alternatives. Ask why that comparison feels suspicious. Then give five plain questions: what does the application mean/do; how do programs exchange data end to end; how does a packet reach an IP destination; how does IP fit a constrained local link; how is the immediate next-hop frame sent?

Watch for

Students should distinguish the question being solved before seeing or discussing example technologies.

Validate

Application / Transport / Network / Adaptation / Local link are labels for five different engineering responsibilities.

Correct if needed

Do not ask students to infer unfamiliar protocol names here. Correct only the responsibility boundary. Technology names arrive in Activity 4 after the job is understood.

Landing point / transition

Land on stack = ordered responsibilities. A product or suite can cover several jobs, so a name is not automatically one layer.

04
Activity 4 of 9

Attach technical names to the jobs

Show the engineering problem first; reveal IPv6, 6LoWPAN, TCP, UDP or Thread only afterwards.

8–9 min work · no restitutionCore cap · 6 min
Operational trigger to stage

For each dossier card, students first read a plain engineering problem, e.g. “carry IPv6 over very small local frames” or “provide an ordered byte stream with recovery”. They choose which job this evidence supports and what remains unknown. Only then reveal the technical name.

Watch for

The key move is two-sided: what can I conclude from this evidence, and what can I still not conclude?

Validate

IPv6, 6LoWPAN, TCP and UDP can be attached to jobs already understood. Thread is useful precisely because it shows that one named suite can package several networking jobs.

Correct if needed

Do not turn this into a recognition quiz. UDP is a minimal datagram transport, not “bad TCP”; Thread does not decide the application exchange protocol.

Landing point / transition

Students now have names for lower-stack mechanisms without having needed prior networking vocabulary.

05
Activity 5 of 9

Three ways applications can exchange information

Introduce MQTT, CoAP and HTTP as names for three already-understandable application exchange styles.

9–10 min work · no restitutionCore cap · 7 min
Operational trigger to stage

Start with three service needs in plain language: publish events without naming each consumer; read/update/observe a resource on a constrained device; expose a conventional web/API resource. Then attach MQTT, CoAP and HTTP respectively, with one short portrait of the interaction each supports.

Watch for

Students should choose from service behaviour and constraints, not from slogans such as “IoT = MQTT”.

Validate

MQTT is brokered publish/subscribe; CoAP is lightweight resource-oriented request/response with mechanisms such as Observe; HTTP is web/API resource request/response. These are application-layer choices that still depend on lower responsibilities.

Correct if needed

Do not equate HTTP with TCP as an absolute rule, and do not present CoAP as “UDP without reliability”. Keep the core distinction at application behaviour; transport details are the next boundary.

Landing point / transition

Land on: application protocols give a concrete form to conversations, but successful exchange still does not ensure shared meaning.

06
Activity 6 of 9

The bytes arrived — why is the data unusable?

Separate endpoint location, application naming and shared meaning before naming interoperability.

9–11 min work · 7–8 min restitutionCore cap · 12 min
Operational trigger to stage

Show the successfully received payload {"value":812}. Ask three questions in order: where did it come from / where is it sent; which application resource or channel is targeted; what does 812 actually mean? Only after those distinctions introduce semantic interoperability.

Watch for

Students mixing IP/port with resource path/topic, or treating JSON syntax as sufficient meaning.

Validate

Delivered bytes can be syntactically valid and still unusable because phenomenon, unit, source, time or quality are unknown.

Correct if needed

An IP address locates a network endpoint; /sensors/17 or an MQTT topic names an application resource/channel; neither supplies the measurement semantics by itself.

Landing point / transition

Now name the problem: interoperability includes shared interpretation, not merely successful transport.

07
Activity 7 of 9

Build the whole path end to end

Make “compare” versus “compose” explicit before assembling complete stacks.

11–12 min work · 8–9 min restitutionCore cap · 14 min
Operational trigger to stage

Put “MQTT versus Thread” in front of the class and ask a single question: do these names answer the same engineering question? If not, they are not direct alternatives. Then let students assemble two full paths and explain which names coexist because they solve different jobs.

Watch for

Students comparing protocol names across different responsibilities instead of first locating the job.

Validate

Compare within the same responsibility; compose compatible mechanisms across different responsibilities.

Correct if needed

MQTT and Thread can coexist. Thread covers lower networking responsibilities; MQTT defines an application exchange pattern. “Thread vs TCP” is likewise not a clean same-job comparison.

Landing point / transition

The path is now technically coherent. The next question is not another protocol name: what behaviour can this complete system actually guarantee?

08
Activity 8 of 9

Reliable what, exactly?

Start from an ACK-loss incident; introduce guarantee scope and QoS only after the ambiguity is felt.

11–13 min work · 8–10 min restitutionCore cap · 14 min
Operational trigger to stage

Use the concrete incident: the actuator moves, its acknowledgement is lost, and the sender retries. Ask what may happen before mentioning QoS. Then separate four possible objects of a reliability claim: bytes, protocol message, logical operation, physical state.

Watch for

Whether students explicitly name the object and boundary of a guarantee instead of saying only “reliable”.

Validate

A guarantee is meaningful only with a scope. Transport, application protocol, application logic and physical feedback protect different objects and often have to cooperate.

Correct if needed

Define QoS here if the term is used: a protocol-specific set of delivery behaviours/levels, not a universal reliability switch. MQTT QoS 2 does not by itself guarantee exactly-once physical actuation.

Landing point / transition

Land on scoped guarantees: reliable bytes ≠ unique message ≠ unique operation ≠ verified physical effect.

09
Activity 9 of 9

Explain one failure from end to end

Tell a causal story instead of blaming “the network” or a protocol name.

7–8 min work · 6–7 min restitutionCore cap · 8 min
Operational trigger to stage

Give one service failure where some lower mechanism behaved exactly as specified. Students trace: required outcome → first boundary that was insufficient → observed effect → mechanism that could address it → residual risk.

Watch for

Whether the explanation identifies the first insufficient contract rather than naming a generic layer as faulty.

Validate

A strong failure analysis follows the causal chain from required service outcome to the scope/mechanism that failed to protect it.

Correct if needed

“TCP worked” and “MQTT QoS worked” can both be true while the application or physical service still fails.

Landing point / transition

Close the whole story: conversation → sequence → jobs → protocol names → meaning → composition → guarantee → failure.

Reference plate / step further

Failure trace: required guarantee · object/scope guaranteed · mechanism · observed failure · revision · residual risk.
