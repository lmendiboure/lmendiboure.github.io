IoT Systems Design · Session 2 Notes
Projector Student
Instructor-facing facilitation notes

One communication arc.
Not two courses at once.

The focused Session 2 has one objective: make a campus exchange implementable. Students move from service behaviour to message order, four stack responsibilities, protocol composition and shared data meaning. The pages deliberately contain less reference material and fewer concurrent visual blocks.

Instructional ruleProblem → one distinction → student move → formal term. When a worked example is needed, show one complete example first, then remove part of the support in the next task.
Scope boundaryQoS, retry semantics, exactly-once claims, duplicate-operation crash windows and end-to-end failure tracing are moved to Session 4 — Robustness. Do not “preview-teach” them here beyond reminding students that a digital ACK is not automatically proof of a physical effect.

01
Conversation

Describe the exchange before naming it

Worked telemetry example, then three student cases.

6 min work · 5 min STOP
Purpose

Attach pattern vocabulary to observable behaviour: initiator, receiver set and waiting condition.

Validate

Request/response, publish/subscribe and command/ACK are names for service behaviour, not protocol implementations.

Watch

If students say MQTT/HTTP, ask them to restate what the service must do without a product/protocol name.

02
Message order

Make the command sequence visible

Order command, digital ACK and physical-state evidence.

7 min work
Validate

A message sequence/choreography expresses who sends what and in what order.

Broker

Introduce the word only after the one-to-many requirement appears: an intermediary redistributes publications to interested subscribers.

03
Stack jobs

Use four responsibilities only

Application · Transport · Network · Local access.

7 min work · 5 min STOP
Reason

Five rows plus unfamiliar protocol names created unnecessary element interactivity for novices. Adaptation remains technically real but is not a fifth manipulation target today.

6LoWPAN

Name it later as the IPv6 adaptation used on constrained IEEE 802.15.4 links. Students should recognise its role without having to classify it as a separate layer in this session.

04
Worked stack

Example first, partial completion second

MQTT/TCP/IP/Wi-Fi → partially completed CoAP/UDP/IPv6/Thread case.

8 min work
Do

Read the full stack aloud once from application down to local access. Then let students fill only the two missing rows of the second case.

Do not

Turn Thread, 6LoWPAN, IPv6, TCP and UDP into five independent recognition cards. Thread is best presented here as an IPv6-based lower networking stack/profile.

05
Application protocols

Use one compact MQTT / CoAP / HTTP comparison

The table is reference; three service decisions are the activity.

8 min work · 5 min STOP
Validate

MQTT: brokered publish/subscribe. CoAP: resource-oriented constrained exchange. HTTP: conventional web/API exchange.

Boundary

These are application protocols. None replaces transport, IP or local access.

06
Composition

Compose — then audit compatibility

Students build one path, inspect a questionable cross-layer pairing, then test what a lower-path change really forces them to revisit.

9 min work
Key sentence

Compare candidates within the same responsibility; compose compatible mechanisms across responsibilities.

Evidence

Ask where MQTT → UDP should first be challenged, then why a Wi-Fi → Thread change does not automatically invalidate every upper-layer decision. Keep the caveat explicit: modular composition still requires compatible interfaces and acceptable constraints.

07
Shared meaning

Repair {"value":812}

Quantity, unit, time and source make the measurement usable.

7 min work · 5 min STOP
Separate

Network address = where packets go. URI/topic = application resource/channel. Semantic contract = what the value means.

Counterexample

{"value":25} can mean 25 °C or 25 %RH. Transport and syntax may both be correct while interpretation fails.

08
Integration

Defend one implementable exchange

Service → interaction → application protocol → lower path → reason.

8 min work · 6 min FINAL STOP
Success criterion

The group can explain the design without beginning with “we chose MQTT/Thread because it is IoT”. Every named mechanism answers an explicit service or deployment need.

Close

Use the synthesis chain: Behaviour → Sequence → Stack → Composition → Meaning. Then state explicitly that robustness/guarantee semantics return in Session 4.
