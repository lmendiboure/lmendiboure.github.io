How do things communicate?

Same nine-activity skeleton as Student and Projector. Session 2 is intentionally longer than Session 1: protocol composition is followed by an explicit delivery-semantics activity before failure testing.

01
Activity 1 of 9

Describe the conversations

Distinguish interaction patterns before protocol vocabulary.

5–6 min work · 5–6 min restitution
Watch for
  • Initiator, recipients, reply expectation, timing.
Validate

Pattern follows service semantics.

Correct if needed

Do not reduce everything to “client/server”; pub/sub is more than one-to-many.

Landing point / transition

Land on service need → interaction pattern.

Reference plate / step further

Reference map: request/response · command/ack · publish/subscribe · observe/notify · event notification · streaming; one-to-one / one-to-many; direct vs broker-mediated.

02
Activity 2 of 9

Draw a message choreography

Externalise message order and coupling.

7–8 min work · 5–6 min restitution
Watch for
  • Intermediary roles and missing replies/acks.
Validate

Same topology can support different choreography.

Correct if needed

Broker ≠ generic gateway; database is not automatically on every critical path.

Landing point / transition

Land on topology ≠ choreography.

Reference plate / step further

Know actor/message roles: producer, consumer, gateway/proxy, broker; telemetry, query/response, command/ack, event/notification.

Activity 3 of 9

Build the stack by responsibility

Create the abstraction model for protocol composition.

6–7 min work · 5–6 min restitution
Watch for
  • Routing vs transport reliability; semantics placed in transport.
Validate

Application/Transport/Network/Adaptation/Link is a working model.

Correct if needed

Ports belong to transport; topics/resources to application; 6LoWPAN to adaptation.

Landing point / transition

Land on stack = ordered responsibilities; suites can span rows.

04
Activity 4 of 9

Discover network and transport pieces

Attach names after responsibility mapping.

8–9 min work · no restitution
Watch for
  • IPv6, 6LoWPAN, TCP, UDP, Thread placement.
Validate

Thread is IPv6-based IoT networking over IEEE 802.15.4 / 6LoWPAN foundation.

Correct if needed

UDP “minimal datagram service” is not equivalent to “bad/unusable”.

Landing point / transition

Continue directly to application protocols.

05
Activity 5 of 9

Discover application exchange protocols

Separate application semantics from underlying transport/network.

9–10 min work · no restitution
Watch for
  • MQTT pub/sub; CoAP constrained resource exchange; HTTP request/response.
Validate

MQTT commonly composes with TCP; CoAP canonically with datagram transport.

Correct if needed
  • HTTP is not synonymous with TCP.
  • CoAP Confirmable messages add reliability.
Landing point / transition

Continue to semantic interoperability.

06
Activity 6 of 9

Make the exchange interoperable

Show that successful message transport does not guarantee shared meaning.

9–11 min work · 7–8 min restitution
Watch for
  • Unit, phenomenon, source, timestamp, location, quality.
  • Distinction between IP address, port, hostname, resource URI/path and MQTT topic.
Validate

Protocol interoperability and semantic interoperability are different problems.

Correct if needed

A JSON syntax is not a semantic model by itself; an MQTT topic is not a network address.

Landing point / transition

Land on bytes → syntax/schema → context → shared meaning.

07
Activity 7 of 9

Compose complete stacks

Compose compatible layers instead of comparing unrelated names.

11–12 min work · 8–9 min restitution
Watch for
  • A: 802.15.4 → 6LoWPAN → IPv6 → UDP → CoAP.
  • B: Wi-Fi → IPv6 → TCP → MQTT (exercise assumptions).
Validate

Illustrative compositions, not the only valid stacks.

Correct if needed

MQTT vs Thread or Thread vs TCP are abstraction-level mismatches.

Landing point / transition

Land on compare within responsibility; compose across responsibilities. Then ask the missing question: what delivery semantics does the service need?

08
Activity 8 of 9

Choose the delivery semantics

Make “reliability” precise by naming the object and scope being guaranteed.

11–13 min work · 8–10 min restitution
Watch for
  • Students confusing message delivery with application effect.
  • Whether offline delivery is treated as a state/persistence question.
  • Mechanisms placed at only one layer when end-to-end cooperation is needed.
Validate

Expected service mapping: ambient telemetry → best effort can be acceptable; critical alert → at-least-once message delivery; ventilation command → prevent duplicate operation effect; temporary disconnect → persistence/replay when the service requires it. These needs can require cooperation across responsibilities.

Correct if needed
  • MQTT QoS 2 is exactly-once at the MQTT message-delivery scope, not a universal exactly-once physical-effect guarantee.
  • CoAP ACK confirms receipt of a Confirmable message; it does not by itself prove the physical action succeeded.
  • TCP provides reliable in-order bytes, not idempotent application operations.
Landing point / transition

Land on scoped guarantees: transport delivery, application-protocol delivery, application operation semantics, intermediary persistence, physical feedback. Then stress-test one explicit guarantee.

Reference plate / step further

09
Activity 9 of 9

Stress-test the exchange

Locate failures at the mechanism/semantic level that can fix them.

7–8 min work · 6–7 min restitution
Watch for
  • Groups should name the required guarantee before selecting a mechanism.
  • Look for lower layers behaving correctly while the service still fails.
Validate

Failure analysis is strongest when it traces required guarantee → scope → mechanism → observed failure → revision.

Correct if needed

Do not let “TCP worked” or “MQTT QoS worked” stand in for application/physical correctness.

Landing point / transition

Close on need → pattern → meaning → responsibilities → composition → delivery semantics → failure test.

Reference plate / step further

Failure trace: required guarantee · object/scope guaranteed · mechanism · observed failure · revision · residual risk.
