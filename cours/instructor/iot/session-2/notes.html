Instructor-facing facilitation notes · Session 2

How do things communicate?

Same nine-activity skeleton as Student and Projector. Session 2 is intentionally longer than Session 1: protocol composition is followed by an explicit delivery-semantics activity before failure testing. The student surface now privileges constructed artefacts over answer-box prose: the Core route contains no free-text textarea.

Protocol evidence block: Activities 4–5 intentionally run without a full STOP. They are evidence-acquisition activities with embedded audits; do not pre-teach their mappings in the Activity 3 restitution. If several groups still hold the same factual misconception after the audit, use a 60–90 s calibration, then continue. The full protocol map is institutionalised when students compose complete stacks in Activity 7.

Restitution contract: for Activities 1, 2, 3, 6, 7, 8 and 9, keep the student artifact visible, compare reasoning, reveal the counterexample, then formalise with What to keep. Students unlock the same concept into their persistent Field guide before continuing. After the Activity 9 STOP, use the Memory Lock before displaying the final synthesis. Four optional Challenge-me routes are available in Activities 3, 6, 7 and 8; use them for conceptual depth, not as a reward for speed.

Non-negotiable outcomes

  • Students distinguish protocol interoperability from semantic interoperability.
  • Students reason about scoped delivery guarantees and end-to-end correctness.

Activity 5 of 9

Discover application exchange protocols

Separate application semantics from underlying transport/network.

9–10 min work · no restitutionCore cap · 7 min
Operational trigger to stage

Leila now has the service profiles and lower-layer responsibilities; what is missing is an application exchange mechanism. Do not have her repeat the pattern-selection task.

Watch for
  • MQTT pub/sub; CoAP constrained resource exchange; HTTP request/response.
Validate

Make the exchange interoperable

Show that successful message transport does not guarantee shared meaning.

9–11 min work · 7–8 min restitutionCore cap · 12 min
Operational trigger to stage

Activity 7 of 9

Compose complete stacks

Compose compatible layers instead of comparing unrelated names.

11–12 min work · 8–9 min restitutionCore cap · 14 min
Operational trigger to stage

Yanis finds both “MQTT over TCP” and “MQTT versus Thread” in the same integration document. The contradiction is the trigger; students must discover why through composition.

Watch for
  • A: 802.15.4 → 6LoWPAN → IPv6 → UDP → CoAP.
  • B: Wi-Fi → IPv6 → TCP → MQTT (exercise assumptions).
Validate

Illustrative compositions, not the only valid stacks.

Correct if needed

MQTT vs Thread or Thread vs TCP are abstraction-level mismatches.

Landing point / transition

Land on compare within responsibility; compose across responsibilities. Then ask the missing question: what delivery semantics does the service need?

08
Activity 8 of 9

Choose the delivery semantics

Make “reliability” precise by naming the object and scope being guaranteed.

11–13 min work · 8–10 min restitutionCore cap · 14 min
Operational trigger to stage

Amina rejects the acceptance claim “MQTT QoS 1 + TCP = reliable command” because the scope of “reliable” is undefined and the sentence contains no evidence of physical effect.

Watch for
  • Students confusing message delivery with application effect.
  • Whether offline delivery is treated as a state/persistence question.
  • Mechanisms placed at only one layer when end-to-end cooperation is needed.
Validate

Expected service mapping: ambient telemetry → best effort can be acceptable; critical alert → at-least-once message delivery; ventilation command → prevent duplicate operation effect; temporary disconnect → persistence/replay when the service requires it. These needs can require cooperation across responsibilities.

Correct if needed
  • MQTT QoS 2 is exactly-once at the MQTT message-delivery scope, not a universal exactly-once physical-effect guarantee.
  • CoAP ACK confirms receipt of a Confirmable message; it does not by itself prove the physical action succeeded.
  • TCP provides reliable in-order bytes, not idempotent application operations.
Landing point / transition

Land on scoped guarantees: transport delivery, application-protocol delivery, application operation semantics, intermediary persistence, physical feedback. Then stress-test one explicit guarantee.

09
Activity 9 of 9

Stress-test the exchange

Locate failures at the mechanism/semantic level that can fix them.

7–8 min work · 6–7 min restitutionCore cap · 8 min
Operational trigger to stage

Sam brings a service failure in which the network or protocol behaved as specified while the report simply blames “communication”. Students must resolve that ambiguity in the activity, not in the trigger.

Watch for
  • Groups should name the required guarantee before selecting a mechanism.
  • Look for lower layers behaving correctly while the service still fails.
Validate

Failure analysis is strongest when it traces required guarantee → scope → mechanism → observed failure → revision.

Correct if needed

Do not let “TCP worked” or “MQTT QoS worked” stand in for application/physical correctness.

Landing point / transition

Close on need → pattern → meaning → responsibilities → composition → delivery semantics → failure test.

Reference plate / step further

Failure trace: required guarantee · object/scope guaranteed · mechanism · observed failure · revision · residual risk.
