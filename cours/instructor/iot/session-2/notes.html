IoT Systems Design · Session 2 Notes
Projector Student
Preparation notes · not a live dashboard

One visible stack.
Build it progressively.

The session is no longer organised as several independent protocol exercises. The same map is kept throughout: service behaviour → Application → Transport → Network → Local path → Shared meaning. The Projector progressively fills that map; the Student page practices only the decision currently being introduced.

Live rule
Use the Projector to establish the shared mental model after each activity. Do not introduce protocol names before their row is visible. Do not use these notes live unless you need a technical reminder.
01

Service conversation

Formalise behaviour before protocol names.

6 min work · 4 min discussion
Why now

Students need to know what the service exchange is asking for before any protocol comparison is meaningful.

Keep

One-way, request/response, publish/subscribe and command/ack are interaction patterns, not protocol implementations.

Transition

“We know what the conversation must do. Now what separate communication jobs make that conversation travel?”

02

Four-row stack map

Application · Transport · Network · Local path.

8 min work · 5 min discussion
Why now

This is the central mental model. Do not introduce Thread or lower-path implementation details here.

Projector move

After the sort, reveal one familiar full stack: HTTP/1.1 → TCP → IP → Wi-Fi.

Transition

“Now that the rows exist, we can finally compare names that belong to the same row.”

03

Application protocols

MQTT · CoAP · HTTP all appear on the Application row.

8 min work · 5 min discussion
Validate

MQTT is the clean reference fit for brokered publish/subscribe; CoAP for constrained resource-oriented exchange; HTTP for conventional web/API integration.

Nuance

Alternative implementations exist. Use green for the reference fit, amber for plausible contextual alternatives, red only for a poor fit to the stated case.

Transition

“The top row is filled. What mechanisms carry that application exchange underneath?”

04

Transport + IP

Put TCP/UDP and IP/IPv6 in their rows.

7 min work
Reference path

MQTT requires an ordered/lossless underlying stream; TCP is the teaching reference. Base CoAP uses UDP. HTTP/1.1 is shown over TCP.

Do not overclaim

Say “reference path used today”, not “the only possible transport forever”.

Transition

“Application, transport and network are placed. What changes when the device reaches that network through a different local connectivity path?”

05

Local path + Thread

Introduce Thread only after the upper rows are established.

8 min work · 5 min discussion
Define before using

Thread is an IPv6-based low-power mesh networking stack using IEEE 802.15.4 radios. Keep that as the student-facing definition.

Projector move

Show CoAP/UDP/IPv6 over Wi-Fi beside CoAP/UDP/IPv6 over Thread/802.15.4. The unchanged upper rows are the lesson.

If students ask about how IPv6 fits constrained 802.15.4 frames, 6LoWPAN is the adaptation mechanism; do not make it a core choice today.
Transition

“The stack can now deliver the message. Can the receiver actually interpret the payload?”

06

Shared meaning

Delivery ≠ interpretation.

6 min work · 4 min discussion
Keep

Quantity, unit, time and source are semantic information. IP addresses, topics and URIs solve different identification/delivery problems.

Counterexample

{"value":25} can mean 25 °C or 25 %RH even when every lower protocol worked perfectly.

Transition

“Every piece now has a place. Build one complete stack from the service need down.”

07

Complete campus stack

One end-to-end integration exercise.

9 min work · 7 min final discussion
Success criterion

Students can say why MQTT/CoAP/HTTP are comparable, why TCP/UDP sit below them, why IP is different again, and where the local connectivity sits.

Close

End on the same map shown all session: behaviour → Application → Transport → Network → Local path → Shared meaning.
