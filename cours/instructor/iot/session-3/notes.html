IoT Systems Design · Session 3 Notes
Projector Student
Instructor-facing facilitation notes

Place functions from constraints.
Do not sell “edge”.

Session 3 has one conceptual arc: decide where work executes. Students begin with device / nearby / remote in ordinary language, then discover why data movement, latency, resource feasibility, data minimisation and scale change the placement. The term edge computing is introduced only after a nearby node is visibly executing application work.

Instructional ruleFunction → constraint → feasible zones → boundary → defended placement. If a student begins with “edge is better”, ask which function and which constraint make nearby execution necessary.
Scope boundaryDo not turn connectivity assumptions into a failure/retry lesson. QoS, retransmission, duplicate effects, unavailable dependencies and recovery remain Session 4.

01
Functions

Place work before naming architectures

Six functions, three plain deployment zones.

7 min work · 5 min STOP
Purpose

Break the common “the whole application goes to cloud/edge” mental model. The artifact should already show that different functions can live in different zones.

Accept

Multiple placements are defensible because constraints have not yet been introduced. The value is in identifying which choices feel conditional.

Watch

Do not correct early placements from your preferred architecture. Ask what assumption made the choice feel reasonable.

02
Data movement

Make data volume visible without fake precision

Compare application-record counts, not invented byte-perfect network costs.

8 min work
Calculation

Every 5 s: 17,280 records/day/sensor = 3,456,000/day for 200 sensors. 1-min summary: 288,000/day. 5-min routine summary: 57,600/day + immediate events.

Boundary

Aggregation reduces routine transfer but changes fidelity and requires compute/state somewhere before the remote boundary.

03
Response budget

Use scenario evidence, not “edge is low latency”

Three budgets against an explicit exercise planning envelope.

7 min work · 5 min STOP
Precision

The 5–15 / 20–60 / 90–220 ms ranges are deliberately labelled as planning assumptions for this exercise. Never present them as universal device/edge/cloud latency figures.

Concept

The farthest feasible zone may still be desirable for maintainability or resource reasons. Latency only rules out zones when the service budget makes it binding.

04
Feasibility

Rule zones out before optimising them

Threshold, aggregation, image inference, model training.

9 min work
Teaching point

Placement is first a feasibility problem. A zone that cannot satisfy compute/memory/energy/storage needs is not a candidate regardless of latency.

Do not overclaim

The resource envelopes are hypothetical campus hardware classes. They are not definitions of all IoT devices, gateways or clouds.

05
Data minimisation

Use a different modality to force transfer

Camera occupancy case: raw images cannot leave the building.

7 min work · 5 min STOP
Expected reasoning

Camera cannot run the model; remote raw-video processing violates the stated boundary; nearby building compute is therefore the natural feasible location under the given assumptions.

Step further

Even a derived occupancy count still needs source/time/confidence context. This reconnects cleanly to Session 2 shared meaning.

06
Edge role

Name edge computing after the role is visible

Forwarding gateway versus nearby application execution.

7 min work
Formalise

In this course, “edge” is used as a placement role: application work is executed closer to data sources/users instead of exclusively in remote infrastructure. It is not a protocol.

Nuance

MEC is a specific ETSI multi-access edge framework. Do not use MEC as a synonym for every local gateway. NIST fog/edge terminology is broader and historically heterogeneous.

07
Split pipeline

Make the cut implementable

Six functions + one nearby→remote representation.

9 min work · 5 min STOP
Success criterion

The group can state what crosses the boundary, at what semantic level, and which functions/state remain on each side.

Misconception

“Device → edge → cloud” is not yet an architecture. It becomes one when responsibilities and interfaces at the cuts are explicit.

08
Revision

Change one assumption, revise minimally

Scale ×20, tighter response budget or halved device-energy budget.

7 min work · 5 min FINAL STOP
Validate

Students should identify a causal link from changed assumption → invalidated placement rationale → one revised function/zone. Do not reward wholesale redesign unless they can show why it is necessary.

Transition

Session 4 changes the question from “where should it run?” to “what happens when delivery, nodes or dependencies fail or retry?”
