01
STOP 1

What makes these systems IoT?

Goal: use disagreement over application domains to create the need for a cross-domain systems definition.

Target · 6–8 min
Listen for
  • Students classify the same object differently because they focus on user, infrastructure, physical setting or service.
  • They notice sensing/actuation and a digital service recur across cases.
What to validate

Several domain labels can be defensible. The classification is not the learning objective; the recurring physical-to-digital structure is.

Correct if needed
  • Do not reduce IoT to “anything connected to the Internet”.
  • Do not present the working definition as the only universal definition in the literature.
If discussion stalls

Ask: “What would make a normal laptop browsing a website different from these eight cases?” Then ask whether a connected actuator with no sensor could still be IoT.

Work screen

Leave the WORK screen projected while students classify the eight systems. The public screen states the deliverable and the guardrail; do not add the working IoT definition verbally.

Reality check

The three system patterns (cold chain, smart metering, industrial monitoring) are examples of the same physical-to-digital skeleton, not canonical architectures. Ask what is invariant (physical role + observation/action + communication + digital service) and what can vary (domain, device, network, backend).

Live Board · Capture

When: after every group has committed its classifications. Type only 4–8 short recurring features from the room; merge synonyms rather than transcribing. Use the board to ask which features really define the common systems pattern. Do not treat frequency as correctness.

Answer to land on

Working view for this course: IoT systems connect physical entities that are observed or acted upon to digital services through communication and computation. “Connected” alone is not a useful boundary.

Transition

“If IoT can describe very different domains, we cannot start from one standard architecture. Let’s build one system from its purpose and information flows.”

02
STOP 2

What is the architecture actually representing?

Goal: separate responsibilities, physical components and information flows before technology names enter the design.

Target · 7–9 min
Listen for
  • Some groups draw physical boxes; others draw functions.
  • Some omit users, storage, alerts or return paths.
  • Flows expose dependencies not visible from boxes alone.
What to validate

Different physical decompositions can be valid if the required responsibilities and end-to-end flows are present and explainable.

Correct if needed
  • “Cloud”, “MQTT”, “LoRaWAN” or “Raspberry Pi” are not substitutes for identifying architectural responsibility.
  • The five-role lens is not a mandatory five-layer architecture.
If discussion stalls

Use the one-Raspberry-Pi challenge. Ask separately: “How many boxes?” and “How many responsibilities?”

Work screen

Leave the Architecture v1 WORK screen projected. Students should produce components plus labelled flows. If they ask whether a gateway/cloud/database is “required”, answer by asking which responsibility or flow they need it to serve.

Reality check

The displayed campus architecture is deliberately one defensible functional decomposition, not a reference answer to copy. Use it to ask what could merge, move or replicate while preserving the service. The key is that responsibilities and flows survive even when physical placement changes.

Live Board · Structure

When: after groups have Architecture v1. Build a minimal collective graph from their contributions: about 4–6 boxes and only flows the room can name. If two groups disagree on where Compute or Store lives, keep that disagreement visible rather than resolving it prematurely. The board is a class model, not the reference architecture.

Answer to land on

Architecture lens: Sense/Act · Communicate · Compute · Store · Use. These are responsibilities, not mandatory devices or layers. Track labelled information flows between them.

Transition

“Now that we know what communicates with what, the next question is not yet ‘which radio?’. It is: what does each of these flows require?”

03
STOP 3

Which requirements really drive a flow?

Goal: attach engineering vocabulary to plain-language constraints and break the idea of one system-wide requirement profile.

Target · 6–8 min
Listen for
  • Different groups legitimately rank different priorities because assumptions are underspecified.
  • Students say “fast” when they mean latency, data rate or both.
  • Energy matters differently for powered and battery nodes.
What to validate

A requirement is useful when tied to a specific service or flow and to an explicit assumption. Different flows can have different Top 3 constraints.

Correct if needed
  • Latency = delay; throughput/data volume = amount/rate of data.
  • Reliability is not the same as “always connected”. Define what must be delivered and under which conditions.
Vocabulary mapping

How far? → Range · How much data? → Data volume/throughput · How soon? → Latency · How dependable? → Reliability · Limited energy? → Energy · How many? → Scale · Does it move? → Mobility · What exists? → Infrastructure · What can we afford? → Cost.

Work screen

Keep the constraint-selection deliverable visible and resist technology questions until students have a Top 3 and can attach at least one priority to a concrete flow.

Reality check — arithmetic

Worked assumptions: 30 nodes × 4 values × 4 bytes, once per minute. That gives 16 B/report, 480 B/min across the deployment and 691,200 B/day ≈ 0.69 MB/day of raw values. This deliberately excludes headers, timestamps, retransmissions, security overhead and protocol behaviour. The camera contrast assumes one 100 kB image every 5 s: 17,280 images/day ≈ 1.728 GB/day. Use the contrast to separate data volume/throughput from latency: a 5 s alert deadline can be demanding even when the periodic sensor payload is tiny.

Live Board · Compare

When: only after each group has fixed its Top 3. Tally one dominant requirement per group. Use divergence to ask which mission fact or flow explains the difference. Never use the majority bar as a correctness signal; commit first, aggregate second, discuss third.

Answer to land on

Do not compare technologies against a generic “IoT requirement list”. Compare candidate solutions against the dominant requirements of each important flow.

Transition

“We now have a problem description that is precise enough to ask what kinds of communication structures could satisfy it.”

04
STOP 4

How should technology choices be justified?

Goal: consolidate network shapes and abstraction levels, then connect technology choice to implicit infrastructure assumptions.

Target · 10–12 min
Listen for
  • Students choose the same technology for different reasons.
  • Some reason from distance only; bring them back to traffic, energy and infrastructure.
  • Some compare objects at different abstraction levels as if they were equivalent.
Decision rule

Communication problem → network shape → technology family → implicit dependencies. Technology names should be attached after the structure and requirements are understood.

Misconceptions to catch
  • LoRa = LoRaWAN.
  • 802.15.4 automatically implies mesh.
  • Unlicensed spectrum means “no infrastructure”.
  • NB-IoT and satellite are necessarily mutually exclusive.
  • One technology must serve every campus flow.
If discussion stalls

Ask ownership questions: “Who installs the access point/gateway? Who operates the network? What happens if the upstream path disappears?”

Work screen

Leave the WORK screen “Shape first. Name second. Decide last.” projected through Activities 4–6. The public milestones are enough; the detailed facilitation remains here.

Reality check — how to read the numbers

Bluetooth SIG lists LE protocol data rates of 1 Mb/s (LE 1M), 2 Mb/s (LE 2M), 500 kb/s (LE Coded S=2) and 125 kb/s (LE Coded S=8). LoRa Alliance RP002-1.0.3 lists EU863-870 default LoRa DR0–DR5 at roughly 0.3–5 kb/s and includes duty-cycle constraints. Do not present these as application-throughput benchmarks or as proof that one family is “better”; they make visible that “low-power wireless” spans very different operating points. IEEE’s current 802.15.4 description explicitly scopes the standard to PHY and MAC. GSMA’s 2026 deployment guidance treats NB-IoT and LTE-M as complementary cellular LPWA technologies and stresses that network configuration affects device/end-to-end behaviour.

Official sources: Bluetooth SIG · LoRa Alliance RP002 · IEEE 802.15.4 · GSMA Mobile IoT 2026.

Live Board · Compare

When: after deployment choices are committed. Tally the chosen family — including “Not enough info”. Do not interpret the counts until the room has finished committing. Then use the tally to select two contrasting groups and compare the assumptions that produced their choices.

Answer to land on

A defensible technology choice states both why the family fits the flow and what infrastructure or service assumptions it introduces. “Not enough information yet” is a legitimate engineering answer.

Transition

“A design only looks correct while its assumptions hold. Let’s change one assumption and see what the system has to become.”

05
Final debrief

What did the incident teach us?

Goal: make the design revision visible and end on a transferable reasoning loop, not a technology catalogue.

Target · 8–10 min
Listen for
  • Students can name the assumption that changed.
  • They connect that assumption to a requirement under pressure.
  • They can explain why their structural edit addresses only part of the problem.
What to validate

There is not one universally robust architecture. Robustness is relative to explicit failure/operating assumptions and acceptable degraded behaviour.

Correct if needed
  • Adding components is not automatically robustness.
  • Replication, buffering, local processing or alternate connectivity each solve specific failure modes and can create new costs.
Retrieval questions
  • What must be explicit before choosing a technology?
  • Why is 802.15.4 not the same kind of object as LoRaWAN?
  • What changed between v1 and v2?
  • Camera instead of CO₂ sensor: what should be revisited first?
Work screen

Leave the debrief WORK screen visible while students produce v2. Require a visible structural edit rather than only a mitigation sentence, plus one residual risk.

Reality check

The worked Internet-outage example is intentionally causal: upstream path disappears → alert availability/latency is threatened → minimum decision/buffering moves local → cloud synchronization becomes deferred → gateway/radio failure remains. Emphasise that this does not prove “edge is better”; it shows how a changed assumption can justify a specific architectural move.

Answer to land on

Need → functions → architecture → information flows → requirements → candidate technologies → challenge → revision. The central competence is to explain the validity domain of a design decision and revise it when assumptions change.

Close

Do not end by re-listing protocols. End by asking one student to state the reasoning loop in their own words, then show the final chain on the Projector.

Projector operating loop

Two public screens per checkpoint

  • WORK: leave the deliverable, defence prompt and guardrail visible while groups work. Do not operate the projector during this period.
  • RESTITUTION: one stable class surface containing the appropriate Live Board (when useful), 2–3 discussion prompts and one counterexample.
  • Takeaway: reveal the concise formalisation inside the same restitution screen when the discussion has created the need for it.
  • Reality: reveal one concrete artifact, calculation or official technical fact inside the same restitution screen. Takeaway and Reality are mutually exclusive to keep the screen light.

The complexity stays private: LOOK → COMPARE → CHALLENGE → FORMALISE → GROUND is a facilitation sequence in these notes, not a navigation sequence on the projector.

Live Board rule: use only Capture (short ideas), Structure (boxes + flows), or Compare (simple tally). Commit first, aggregate second, discuss third. Omit the board when it adds no signal.

Quick reference

What must students leave Session 1 knowing?

  • IoT is a systems field, not one application domain.
  • Architecture responsibilities are not the same as physical boxes.
  • Information flows are the right unit for many communication requirements.
  • Latency and throughput are different.
  • Technology names sit at different abstraction levels.
  • Choose network shape before technology name.
  • Technology choices imply infrastructure assumptions.
  • “Not enough information” can be a correct engineering conclusion.
  • Architecture validity depends on assumptions.
  • A changed assumption should be traceable to a design revision.
