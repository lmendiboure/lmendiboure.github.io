01
Activity 1 of 7

Map the IoT landscape

Goal: use disagreement over application domains to create the need for a cross-domain systems definition.

Work 6–7 min · Restitution 5–6 min
Listen for
  • Students classify the same object differently because they focus on user, infrastructure, physical setting or service.
  • They notice sensing/actuation and a digital service recur across cases.
What to validate

Several domain labels can be defensible. The classification is not the learning objective; the recurring physical-to-digital structure is.

Correct if needed
  • Do not reduce IoT to “anything connected to the Internet”.
  • Do not present the working definition as the only universal definition in the literature.
If discussion stalls

Ask: “What would make a normal laptop browsing a website different from these eight cases?” Then ask whether a connected actuator with no sensor could still be IoT.

Live Board · Capture

After every group has committed its classifications, type only 4–8 short recurring features from the room. Merge synonyms. Use the board to ask which features really define the common systems pattern; frequency is not correctness.

Reality check

Cold-chain monitoring, smart metering and industrial monitoring instantiate the same physical-to-digital skeleton without sharing the same domain, device, network or backend.

Answer to land on

Working view for this course: IoT systems connect physical entities that are observed or acted upon to digital services through communication and computation. “Connected” alone is not a useful boundary.

Transition

“If IoT can describe very different domains, we cannot start from one standard architecture. Let’s build one system from its purpose and information flows.”

02
Activity 2 of 7

Build architecture v1

Goal: separate responsibilities, physical components and information flows before technology names enter the design.

Work 10–12 min · Restitution 6–7 min
Listen for
  • Some groups draw physical boxes; others draw functions.
  • Some omit users, storage, alerts or return paths.
  • Flows expose dependencies not visible from boxes alone.
What to validate

Different physical decompositions can be valid if the required responsibilities and end-to-end flows are present and explainable.

Correct if needed
  • “Cloud”, “MQTT”, “LoRaWAN” or “Raspberry Pi” are not substitutes for identifying architectural responsibility.
  • The five-role lens is not a mandatory five-layer architecture.
If discussion stalls

Use the one-Raspberry-Pi challenge. Ask separately: “How many boxes?” and “How many responsibilities?”

Live Board · Structure

Build a minimal collective graph from student contributions: about 4–6 boxes and only flows the room can name. Keep disagreements about where Compute or Store lives visible rather than resolving them prematurely.

Reality check

The displayed campus architecture is one defensible functional decomposition, not a reference answer to copy. Ask what could merge, move or replicate while preserving the service.

Answer to land on

Architecture lens: Sense/Act · Communicate · Compute · Store · Use. These are responsibilities, not mandatory devices or layers. Track labelled information flows between them.

Transition

“Now that we know what communicates with what, the next question is not yet ‘which radio?’. It is: what does each of these flows require?”

03
Activity 3 of 7

Expose communication requirements

Goal: attach engineering vocabulary to plain-language constraints and break the idea of one system-wide requirement profile.

Work 6–8 min · Restitution 5–6 min
Listen for
  • Different groups legitimately rank different priorities because assumptions are underspecified.
  • Students say “fast” when they mean latency, data rate or both.
  • Energy matters differently for powered and battery nodes.
What to validate

A requirement is useful when tied to a specific service or flow and to an explicit assumption. Different flows can have different Top 3 constraints.

Correct if needed
  • Latency = delay; throughput/data volume = amount/rate of data.
  • Reliability is not the same as “always connected”. Define what must be delivered and under which conditions.
Vocabulary mapping

How far? → Range · How much data? → Data volume/throughput · How soon? → Latency · How dependable? → Reliability · Limited energy? → Energy · How many? → Scale · Does it move? → Mobility · What exists? → Infrastructure · What can we afford? → Cost.

Live Board · Compare

Only after each group has fixed its Top 3, tally one dominant requirement per group. Use divergence to ask which mission fact or flow explains the difference. Commit first, aggregate second, discuss third.

Reality check — arithmetic

30 nodes × 4 values × 4 bytes once per minute gives 16 B/report, 480 B/min and ≈0.69 MB/day of raw values. A hypothetical 100 kB image every 5 s is ≈1.73 GB/day. These are worked assumptions, not protocol-throughput measurements.

Answer to land on

Compare candidate solutions against the dominant requirements of each important flow, not against a generic IoT requirement list.

Transition

“We now have a problem description precise enough to ask what kinds of communication structures could satisfy it.”

04
Activity 4 of 7

Discover communication patterns

Goal: reason from the communication problem to a network shape before introducing technology names.

Work 5–6 min · No restitution
Students do

Use distance, traffic, energy and available infrastructure to inspect five plain-language network shapes, then reveal the corresponding family names.

Watch for
  • Students jumping directly to a familiar technology name.
  • Treating every network as device → Internet without identifying intermediate infrastructure.
  • Confusing a local link building block with a complete end-to-end architecture.
What must be clear before moving on

Nearby peer, local access point, constrained local building block, gateway-based wide area, and operator-managed wide area are meaningfully different structures.

Projector rule

This activity is WORK only. Do not start a whole-class correction. The activity itself reveals the family names needed for Activity 5.

Transition

Move directly to Activity 5 · Investigate technologies. This preserves the detective task from being spoiled by teacher explanation.

05
Activity 5 of 7

Investigate technologies

Goal: consolidate the network-shape map and distinguish technology families and abstraction levels using the detective, library and official sources.

Work 6–7 min · No restitution
Students do

Commit detective answers, inspect the progressive technology cards, and resolve technical distinctions such as LoRa vs LoRaWAN and IEEE 802.15.4 vs a full stack.

Misconceptions to catch later
  • LoRa = LoRaWAN.
  • 802.15.4 automatically implies mesh.
  • Unlicensed spectrum means “no infrastructure”.
  • NB-IoT and satellite are necessarily mutually exclusive.

Projector rule

This activity is also WORK only. Do not interrupt with a catalogue-style correction. Let Activity 6 force students to use what they just learned.

Transition

Move directly to Activity 6 · Choose under constraints.

06
Activity 6 of 7

Choose under constraints

Goal: use transfer cases and the campus checkpoint to justify a communication choice relative to explicit assumptions and dependencies.

Work 7–8 min · Restitution 8–10 min
Listen for
  • Students choosing the same technology for different reasons.
  • Reasoning from distance alone rather than traffic, energy and infrastructure.
  • Recognition that “not enough information” can be a defensible answer.
Decision rule

Communication problem → network shape → technology family → implicit dependencies.

Pacing

Require at least two transfer cases, not all five, then require the campus checkpoint position. Additional cases are depth.

If discussion stalls

Ask ownership questions: “Who installs the access point/gateway? Who operates the network? What happens if the upstream path disappears?”

Live Board · Compare

Tally each group’s campus checkpoint position: one family could be enough, a mixed design is plausible, or not enough information. The transfer cases provide evidence; they do not create one single technology vote per group.

Reality check — how to read the numbers

Bluetooth LE spans protocol data rates from 125 kb/s (LE Coded S=8) to 2 Mb/s (LE 2M). Familiar EU LoRa DR0–DR5 operating points are roughly 0.25–5.47 kb/s physical bit rate. IEEE 802.15.4 scopes PHY + MAC. Do not present these values as application-throughput benchmarks or as proof that one family is better.

Official sources: Bluetooth SIG · LoRa Alliance · IEEE 802.15.4.

Answer to land on

A defensible technology choice states both why the family fits the flow and what infrastructure or service assumptions it introduces.

Transition

“A design only looks correct while its assumptions hold. Let’s change one assumption and see what the system has to become.”

07
Activity 7 of 7

Stress-test and revise

Goal: make the design revision visible and end on a transferable reasoning loop, not a technology catalogue.

Work 8–10 min · Restitution 6–8 min
Listen for
  • Students can name the assumption that changed.
  • They connect that assumption to a requirement under pressure.
  • They can explain why their structural edit addresses only part of the problem.
What to validate

There is not one universally robust architecture. Robustness is relative to explicit failure/operating assumptions and acceptable degraded behaviour.

Correct if needed
  • Adding components is not automatically robustness.
  • Replication, buffering, local processing or alternate connectivity each solve specific failure modes and can create new costs.
Retrieval questions
  • What must be explicit before choosing a technology?
  • Why is 802.15.4 not the same kind of object as LoRaWAN?
  • What changed between v1 and v2?
  • Camera instead of CO₂ sensor: what should be revisited first?
Reality check

Use the worked Internet-outage example causally: upstream path disappears → alert availability/latency is threatened → minimum decision/buffering moves local → cloud synchronization becomes deferred. This does not prove “edge is better”; it shows how a changed assumption can justify a specific architectural move.

Answer to land on

Need → functions → architecture → information flows → requirements → candidate technologies → challenge → revision. The central competence is to explain the validity domain of a design decision and revise it when assumptions change.

Close

End by asking one student to state the reasoning loop in their own words, then show the final chain on the Projector.

Structural invariant

One session skeleton on every surface

  • Same activity count. Student, Projector and Notes use the same numbered activities.
  • Same titles. Do not rename a student activity for the instructor view.
  • Different depth is allowed. Notes can contain private facilitation logic; the Projector can omit a restitution when interruption would harm the learning sequence.
  • Projector rule: every activity has exactly one WORK screen and zero or one RESTITUTION screen — never more.
  • Activities 4–5: WORK only. Their absence of restitution is pedagogical, not a structural renumbering.
Projector operating loop

Work first, restitution only when useful

  • WORK: leave the deliverable, defence prompt and guardrail visible while groups work.
  • RESTITUTION: one stable class surface with the appropriate Live Board, 2–3 discussion prompts and one counterexample.
  • Takeaway / Reality: reveal in place; never create extra navigation phases.
  • Private complexity: LOOK → COMPARE → CHALLENGE → FORMALISE → GROUND stays in these notes.
  • Live Board: Capture, Structure or Compare only. Commit first, aggregate second, discuss third.
Quick reference

What must students leave Session 1 knowing?

  • IoT is a systems field, not one application domain.
  • Architecture responsibilities are not the same as physical boxes.
  • Information flows are the right unit for many communication requirements.
  • Latency and throughput are different.
  • Technology names sit at different abstraction levels.
  • Choose network shape before technology name.
  • Technology choices imply infrastructure assumptions.
  • “Not enough information” can be a correct engineering conclusion.
  • Architecture validity depends on assumptions.
  • A changed assumption should be traceable to a design revision.
