Teacher guide

Session 1
activity flow

For each block: what students do, what should be visible at the next STOP, and a few prompts worth using in the discussion.

01
Student activity until STOP 1

Map potential IoT systems to application domains

Students receive eight deliberately cross-domain connected physical systems. For each one they choose a main application domain and, when useful, one secondary domain. They do not search for definitions or examples.

Expected before STOPEvery system has a main domain and several should also have a defensible secondary domain. The interesting output is disagreement between groups, not a perfect classification.
Useful for the discussion
  • Start from disagreements rather than correcting every card.
  • Useful ambiguous cases: vaccine shipment = Health / Logistics / Mobility; EV charging = Energy / Mobility / Smart city; school air quality = Environment / Health / Smart city.
  • Expert round: ask a fast group to defend one borderline case. “Connected”, “Internet-connected” and “interacts with the physical world” are not equivalent criteria.
  • The important observation is the breadth of physical environments, actors, infrastructure and constraints covered by IoT.
  • Close with: if these applications are so different, should they all use the same architecture and communication technology?

Message to leave visible: IoT is not one application domain. Similar system concerns reappear across very different physical environments.

02
Student activity until STOP 2

Build architecture v1 from a blank canvas

Students now take one concrete case: campus environmental monitoring. They invent their own components and information flows. Product and protocol names should not be used as architectural answers.

Expected before STOPA readable end-to-end architecture with several functional components and labelled information flows.
Useful for the discussion
  • What did they treat as a component?
  • Separate function, physical component, technology and data flow.
  • One physical node can implement several functions.
  • Use contrasting student architectures rather than presenting a reference architecture immediately.
  • Expert round: after removing a component, students get one architectural move only. Ask what their chosen response fails to solve. This is a useful entry into redundancy, buffering, graceful degradation and alternate paths without teaching those as a catalogue.
03
Student activity until STOP 3

Select communication requirements, then prioritise three

Students first select every requirement dimension that could affect their design. They then make a separate decision and identify the three dominant constraints for the campus scenario.

Expected before STOPA set of relevant communication requirements plus a clearly identified top three.
Useful for the discussion
  • Turn vague words such as “fast”, “far” and “reliable” into precise dimensions.
  • Distinguish latency from throughput/data volume.
  • Different flows in the same architecture can have different requirements.
  • Reference vocabulary: range, data volume/throughput, latency, reliability, energy, scale, mobility, infrastructure, cost.
  • Expert round: compare the requirements of one concrete arrow with the system-wide Top 3. If they differ, ask whether the system-level ranking is hiding an important flow.
04
Student activity until STOP 4

Infer, inspect and choose communication technologies

Students identify technology families from progressively revealed clues, inspect the technology library when needed, then commit to technology choices for several constrained deployment scenarios before seeing the reasoning.

Expected before STOPStudents can distinguish Wi-Fi, Bluetooth LE, IEEE 802.15.4, LoRaWAN and cellular IoT conceptually, and can justify a choice relative to explicit constraints rather than a memorised ranking.
Useful for the discussion
  • LoRaWAN and NB-IoT may both be described as LPWAN while implying very different infrastructures.
  • IEEE 802.15.4 is PHY/MAC, not a complete IoT application architecture.
  • Bluetooth LE has several PHYs and topologies; range is not one fixed number.
  • A technology choice can also imply gateways, local infrastructure, an operator, licensed spectrum, or a core network.
  • Satellite is not simply a sixth equivalent item: distinguish direct access/NTN from satellite backhaul.
  • Use the optional “Layer trap” if available: LoRa ≠ LoRaWAN; IEEE 802.15.4 is not at the same abstraction level as LoRaWAN.
  • The side-by-side comparison supports deeper questions: Bluetooth LE PHY trade-offs, LoRaWAN Class A/B/C and ADR, NB-IoT vs LTE-M, licensed vs unlicensed infrastructure.
  • Expert Claim Lab mixes True, False and Depends statements. Useful cases include “LoRa = LoRaWAN”, battery-powered Wi-Fi, 802.15.4 + mesh, private LoRaWAN, NTN and spectrum-cost claims. Ask which assumption or abstraction level makes the statement valid, invalid or conditional.
  • In deployment cases, students identify the assumption they consider decisive before feedback. Treat the reference driver as a discussion anchor, not a unique correct justification; compare groups that chose the same technology for different reasons.
  • For fast groups on the deployment cases, the “refuse to guess” challenge reinforces that missing requirements should block a premature technology choice.
05
Final student activity

Stress-test the original architecture

Students change one assumption, identify the requirement affected, and select a plausible architectural response. The free-text redesign note remains optional.

Expected at the endStudents can articulate: broken assumption → changed requirement → architectural response.
Useful closing point

An architecture is defensible only relative to assumptions and requirements. If groups tried the compound-failure challenge, they were allowed one architectural change for two failures. Use one answer to show why a response solving one failure may become insufficient when constraints combine. Converge on: Need → functions → architecture → flows → requirements → technology → challenge → revision.
